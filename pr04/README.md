
# ПР-4. Потоки (вариант B)

## Цель
Сравнить потоки и процессы на вычислительной и сетевой задачах, понять роль GIL.

## Задание 1. Сумма 10 млн чисел: медиана из 3 повторов

```
python3 gen_numbers.py
python3 bench_sum.py
```

Вывод (чтение файла в замер не входит, внутри 3 повтора и медиана):

```
1 поток      median=0.087s  ...
4 потока     median=0.089s  ...
4 процесса   median=0.178s  ...
```

Вычислительная задача: **4 потока НЕ ускорили счёт** (0.089 против 0.087) —
это GIL. **4 процесса оказались даже медленнее** (0.178): на столь короткой
задаче суммирования накладные расходы на fork и передачу четвертей списка
через IPC съели весь выигрыш параллелизма. Параллелизм окупается, когда
вычисление дольше, чем стоимость его организации.

## Задание 2. Сетевая задача: 20 URL по localhost

Сервер: `mkdir -p ~/site && cd ~/site; for i in $(seq -w 0 19); do head -c 2000000 /dev/urandom > file$i.bin; done; python3 -m http.server 8000`

```
python3 net_bench.py
```

Вывод:

```
последовательно                    0.141s  ...
ThreadPoolExecutor(8)              0.119s  ...
ProcessPoolExecutor(8)             0.122s  ...
```

Потоки ускорили загрузку (0.119 против 0.141): пока один поток ждёт ответа
сети, остальные качают — CPU свободен. Ускорение скромное, потому что
localhost даёт очень маленькие задержки; на реальной сети выигрыш был бы
в разы. Процессы — примерно как потоки, но дороже на старте.

## Задание 3. Таблица и объяснение через GIL

| Способ | Счёт (CPU) | Сеть/Ввод-вывод | Почему |
|--------|-----------|-----------------|--------|
| 1 поток | 0.087s | 0.141s | базовая линия |
| 4 потока | 0.089s (не ускорило) | 0.119s (ускорило) | GIL: байткод выполняет только один поток, но при ожидании сети/диска поток отпускает GIL |
| 4 процесса | 0.178s (медленнее на короткой задаче) | 0.122s | у каждого процесса свой GIL и свои ядра CPU — CPU-параллелизм есть, но fork+IPC дороги |

GIL (Global Interpreter Lock) в CPython разрешает выполнение байткода только
одному потоку за раз, поэтому потоки не ускоряют чистые вычисления, но
ускоряют ввод-вывод. Процессы не делят GIL и считают параллельно по ядрам,
цена — дорогое создание и передача данных.

## Задание 4. Память: потоки vs процессы

```
python3 memory_demo.py
```

Вывод:

```
после потока, родитель видит: [1, 1, 1, 1, 1] -> поток изменил ОБЩУЮ память
после процесса, родитель видит: [0, 0, 0, 0, 0] -> процесс работал со СВОЕЙ копией
```

Потоки разделяют адресное пространство — изменения видны всем (поэтому нужны
блокировки, см. ПР-6). Процесс после fork получает копию памяти (COW): его
изменения родителю не видны.

## Выводы
Потоки — для ввода-вывода и разделяемых данных (дешево, но GIL и гонки).
Процессы — для CPU-нагрузки и изоляции (параллелизм по ядрам, но дорогой
старт и IPC). В CPython выбор в первую очередь диктуется GIL.
