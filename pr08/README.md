
# ПР-8. Взаимоблокировки (вариант B)

## Цель
Воспроизвести deadlock, реализовать алгоритм банкира и детектор циклов
в графе ожидания.

## Задание 1. Алгоритм банкира

```
python3 banker.py bank1.txt
```

Вывод:

```
SAFE, последовательность: P1 P3 P4 P0 P2
Вводи запросы вида "P1 1 0 2", пустая строка — выход:
P1 1 0 2
  request P1 [1, 0, 2]: GRANT (состояние осталось безопасным)
```

bank1 — классический пример Silberschatz §8.6.3, последовательность совпала
с учебником. Проверка запроса: ресурсы выделяются «в пробном режиме», затем
запускается проверка безопасности; если состояние небезопасно — откат
выделения и отказ (ROLLBACK), если безопасных последовательностей нет вообще
— WAIT/ERROR по причине.

## Задание 2. Небезопасное состояние

```
python3 banker.py bank2.txt
```

Вывод:

```
UNSAFE, последовательность: -
```

То же Allocation и Max, но Available = (0, 1, 0): ни один процесс не может
довыполнить свой Need — безопасной последовательности не существует.

## Задание 3. Детектор по журналу событий (dd.py)

```
python3 dd.py deadlock.log
```

Вывод:

```
рёбра графа ожидания: {'P1': ['P2'], 'P2': ['P1']}
DEADLOCK: P1 -> P2 -> P1
```

Строится граф ожидания (не граф распределения!): ребро A→B = A ждёт ресурс,
который держит B. Журнал: P1 захватил R1, P2 — R2, P1 ждёт R2 (P2 держит),
P2 ждёт R1 (P1 держит). Цикл ищется DFS по трём цветам (белый/серый/чёрный);
серый узел, встреченный повторно, — цикл.

## Задание 4. TrackedLock

```
python3 tracked_lock.py
```

Вывод:

```
пойман вместо зависания: deadlock: поток <id1> ждёт a, удерживаемый <id2>
```

Обёртка над threading.Lock ведёт реестр «кто кого ждёт». Перед захватом
занятой блокировки добавляется ребро «я → владелец» и проверяется, не
замыкается ли цикл; если замыкается — DeadlockError вместо вечного ожидания.
Проверено на классической инверсии порядка: поток 1 берёт a→b, поток 2 — b→a.

## Задание 5. Обедающие философы

```
python3 philosophers.py naive     # deadlock
python3 philosophers.py ordered   # лечение 1: порядок захвата
python3 philosophers.py waiter    # лечение 2: официант (семафор N-1)
```

Выводы:

```
mode=naive:  time=10.0s meals=[0, 0, 0, 0, 0]  <- ЗАВИС: 5 потоков держат левые вилки (deadlock)
mode=ordered: time=0.2s meals=[20, 20, 20, 20, 20] max_wait=['0.004', '0.004', '0.004', '0.005', '0.004']  OK
mode=waiter:  time=0.2s meals=[20, 20, 20, 20, 20] max_wait=['0.007', '0.004', '0.005', '0.005', '0.005']  OK
```

Синхронный старт через барьер гарантирует, что в naive все 5 берут левую
вилку одновременно — дальше каждый ждёт правую у соседа: круговое ожидание,
программа висит (детект по join(timeout), зависшие потоки не дают процессу
выйти — выход через os._exit).

Лечение 1 — иерархия ресурсов: вилки берутся в порядке возрастания «адреса»
(у последнего философа порядок обратный), цикл в графе ожидания невозможен.
Лечение 2 — официант: семафор на N-1 философов за столом, хотя бы один
всегда может взять обе вилки. Обе версии поели по 20 раз, ожидание вилки
не более 7 мс.

## Выводы
Deadlock требует одновременности четырёх условий (взаимоисключение,
удержание-и-ожидание, невытесняемость, круговое ожидание); ломаем одно —
например, упорядочиванием захвата (ordered) или ограничением ожидания
(waiter). Банкир предотвращает небезопасные состояния заранее (откат
запроса), детектор находит уже случившийся deadlock по циклу в графе
ожидания.
